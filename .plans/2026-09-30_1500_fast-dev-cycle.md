# Fast dev cycle: macOS first, Windows as one batched gate

Status: in progress · 2026-09-30

## Measured before starting (2026-09-30, go1.27.1, darwin/arm64)

Two of the causes below were wrong. Kept in the table, struck here:

- **`go run` does not recompile each time.** First `go run ./cmd/irgo-winvm help`
  took 2.04 s, then 0.33 s and 0.13 s. A prebuilt binary: 0.18 s. Go caches the
  linked binary. Change 1 was done anyway, for clarity rather than speed:
  `go:tool` builds `.bin/irgo-winvm` once and every task runs that.
- **`examples/glaze-all` does not crash on macOS.** `-probe` exits 0 with every
  capability OK or cleanly UNSUPPORTED, and interactive mode brings the window up.
  Same result against released glaze and the linked `fix/webview2-stale-registration`.
  `verify` and `verifyevents` also pass on both. No `LockOSThread` change was needed.
  **Change 4 is done: `mise run glaze:mac`** runs all four natively, ~15 s, and
  fails if any does (negative control: a flag glaze-all rejects turned it red).
- **Change 2, half:** `mise run glaze:windows` runs all four on the VM with one
  verdict (1m41s, 30 Sep). Still one push per binary; batching them is what is left.
- **The probes could not fail.** verify, verify-events and probe all exited 0
  whatever happened. Fixed; each was broken on purpose and went red.

- **Why the Windows gate is slow: `utmctl file push` is ~0.4 MB/s.** Measured 30 Sep:
  a 3-byte file 0.19 s, verify.exe (6.9 MB) 17.8 s; `utmctl exec` 0.23 s. So the cost is
  transfer, not per-call overhead, and batching four pushes into one saves nothing.
  **Change 2 is replaced** by: get the bytes to the guest another way.
  - Guest pulls over the VM network: Windows 11 ships curl 8.21. The Mac is
    `192.168.139.3` on `bridge100` from the guest. Blocked: macOS firewall is on
    with stealth mode, so a host HTTP server (tried `python3 -m http.server`) gets
    no connection and curl hangs. Needs the serving binary allowed through the
    firewall (`socketfilterfw --add … --unblockapp`, sudo, and an unsigned binary
    rebuilt by go:tool may need re-allowing), or the user turning stealth off.
  - Or compress before push: stripped (`-s -w`) Go binaries are ~30 % smaller;
    push a zip, expand with `tar -xf` (bsdtar ships with Windows 11).
  - Or a UTM shared directory (SPICE WebDAV / VirtFS): speed unmeasured.
  - **Done, 30 Sep: the reverse direction.** The guest serves SMB and the Mac
    connects out (pure-Go client, nothing mounted, no Mac change). The Mac is
    `192.168.64.1` and the guest `192.168.64.40` on the shared network. The
    `192.168.139.3` above was not that network. 8 MB goes in 1.1 s instead of
    12–14 s, and 49 MB in 1.6 s instead of 1 min 17 s. `glaze:windows` went from
    31 s to 24 s. Zipped utmctl is kept as the fallback. See DEVELOPMENT.md, "How
    a binary gets into the guest", and RESULTS.md.

Remaining: 5 (logs), 3 (poll, not sleep), 6.

## Why

On 2026-09-30 a full Windows check took minutes where it should take seconds. Measured causes:

| Cause | Cost | Where |
|---|---|---|
| One `utmctl file push` + one `app-create` per binary | ~15 s push + ~5 s launch/poll each; `upstream:test:windows` ran 14 suites serially ≈ 4–5 min | `upstream:test:windows`, every `app:create:*` |
| `go run ./cmd/irgo-winvm` per call | recompiles the tool every time (seconds each) | every `app:create:*`, `upstream:test:windows` |
| Fixed `sleep 75/90` after reboots | waits longer than Windows needs, or not long enough | ad-hoc scripts; `vm-repair -reboot` has no "wait until back" |
| Windows as the inner loop | every edit pays the VM round trip | glaze runs natively on macOS, cgo-free, but `examples/glaze-all` crashes there (SIGTRAP in `windowInit`: window created off the main OS thread) |
| Output filtered, not logged | a failure (the 26 s fail-fast run) could not be diagnosed afterwards | ad-hoc scripts |

## Changes

1. **Build the tool once.** A `go:build:tool` step (or `sources`/`outputs` on an existing task)
   builds `.bin/irgo-winvm` when `cmd/` or `internal/utmvm/` change; every task calls `.bin/irgo-winvm`
   instead of `go run ./cmd/irgo-winvm`.
2. **Batch the Windows gate.** `irgo-winvm app-create` accepts several binaries (or a directory):
   one push (a single zip, expanded in the guest), one guest runner script that runs them in order
   in the desktop session and writes one combined result + per-binary exit codes. `upstream:test:windows`
   and a new `app:create:all` (probe, verify, verify-events, glaze-all) use it. Target: 14 suites in
   well under a minute of VM time.
3. **Wait by polling, never sleep.** `vm-repair -reboot` (and anything that reboots) waits until the
   agent answers AND `dev` has a desktop session (`requireDesktopSession` in a bounded loop), then
   returns. Same helper gives `EnsureReady` an optional "desktop too" mode.
4. **macOS first.** Fix `examples/glaze-all` (and any example that opens a window) to lock the main
   OS thread (`func init() { runtime.LockOSThread() }`, darwin needs AppKit on the main thread), and
   add `app:mac:<name>` tasks that build and run the same probes natively on the Mac. Inner loop =
   seconds; Windows = the batched gate before commit.
5. **Always log in full.** Every check task tees its full output to `$IRGO_LOG_DIR/<task>-<stamp>.log`
   (the tool already has a log dir, `doctor` prints it) and prints the path on failure.
6. **Encode the fail-fast proof as a check.** `vm:repair:test`: force a password change at next
   logon + reboot → `app-create -gui` must fail within 60 s with `no desktop session`; then
   `vm-repair -reboot` → wait (3) → `app:create:verify` PASS. Full log kept (5). Replaces the
   uncaptured 26 s run.

## Verify

- `time mise run upstream:test:windows` before/after (record both).
- `mise run app:mac:glaze-all` shows the window and report on macOS without a crash.
- `mise run vm:repair:test` passes end to end with its log path printed.

## Order

5 and 1 first (cheap, help everything), then 4 (fastest loop), 2, 3, 6.
