# Linux VMs in the same tool: a cloud image, one guest seam, the same commands

Status: **phase 1 built and run on its branch** (`feat/linux-vm-phase1`), 2 Oct
2026; phases 2 to 7 not started. The distribution is decided: Ubuntu Server
24.04. What phase 1 measured is in `docs/RESULTS.md` ("A Linux guest by hand"
and "A Linux VM that claude-rig rigs over SSH"). Where the measurements differ
from what is written below, they are right and this text is not:

- the seed CD must be **VirtIO**, not USB: on a USB CD cloud-init never ran
  (M2). Rock Ridge was never the question, `isoBuildImage` already writes it;
- **SSH is on** in the cloud image from its first boot, not "stopped and
  disabled", so the seed turns it off;
- Linux's `vm-ssh.sh` takes the same arguments as `vm-ssh.ps1`, and the
  default account is not a field of the guest description: it is `dev` on both;
- a file named `vm_linux.go` builds only for `GOOS=linux`; the code is in
  `linux_vm.go`.

The rest of this file is the plan as it was written, before anything was run.

The owner wants Linux VMs in this tool, done properly, so that
[claude-rig](https://github.com/joeblew999/claude-rig) can test on UTM VMs for
every OS and drop its OrbStack VM. This plan says which Linux, how it boots
with nobody typing, how it fits the existing commands without a second
implementation, and in what order to build it.

No VM was created, started, stopped or deleted for this plan, UTM was not
touched, and no image was downloaded. Every claim below is marked as one of:

- **read**: read in this repository's code or docs (file and line given), or in
  UTM's source at the `v4.7.5` tag, or on the vendor's documentation page;
- **assumed**: believed from general knowledge, not checked here;
- **to measure**: only a run can settle it. These are collected in
  [What must be measured first](#what-must-be-measured-first).

## Recommendation, in one paragraph

Use the **Ubuntu Server 24.04 ARM64 cloud image** with a **cloud-init NoCloud
seed CD**, on UTM's **QEMU backend**, the same backend Windows uses. The Linux
"install" is then one boot of about a minute or two instead of 45 minutes, and
every host-side mechanism the tool already has (the bundle and `config.plist`,
UTM's import and clone, the guest agent through `utmctl`, the locks, the VM
records, the capacity guard) is used unchanged. The Windows-specific half of
the tool is the *guest* side (`cmd.exe`, batch files, `C:\` paths, PowerShell
scripts, SMB); that is gathered behind **one description of a guest OS inside
`internal/utmvm`**, so each operation keeps one implementation and Linux
supplies different data to it. The OS is chosen where a VM is made
(`vm-create -os linux`) and remembered in the VM's record, so no other command
gains a flag.

## How this relates to issue #7

[Issue #7, "Linux integration"](https://github.com/joeblew999/irgo-windows-vm/issues/7)
is about Linux as a **host**: running the tool on Linux machines with KVM and
Uncloud, driving hypervisors from pure Go (QMP, libvirt,
Virtualization.framework) instead of `utmctl`, Android and iOS devices, and a
contract-first API. This plan is about Linux as a **guest**, on the Mac and UTM
the tool already drives.

| | this plan | left to issue #7 |
|---|---|---|
| Linux guests in UTM on a Mac | yes | |
| the tool running on a Linux host (KVM, libvirt, Uncloud) | | yes |
| replacing `utmctl` and AppleScript with QMP or another pure-Go control path | | yes |
| Android emulators, iOS simulators, containers | | yes |
| an OpenAPI or Fern contract for the Worker and MCP | | yes |

Two things here make #7 easier, and neither decides it:

- **The guest seam.** "Which OS is in the VM" becomes separate from "which
  hypervisor runs it". #7 needs the second axis; it will find the first already
  cut.
- **A hypervisor-neutral image recipe.** A cloud image plus a NoCloud seed
  boots the same way under KVM on a Linux host (assumed), so the Linux golden
  image's recipe carries over.

Phase 6 adds one field to `wire.JobSpec`. The triage comment on #7 names `wire`
as where a contract-first API would start, so that phase is the one place the
two meet, and it waits for #7's direction on the contract.

## 1. Which Linux, and how it boots unattended

### Cloud image or installer ISO

| | cloud image + NoCloud seed | installer ISO + autoinstall |
|---|---|---|
| download | `noble-server-cloudimg-arm64.img`, **591 MB**, qcow2, "QCow2 UEFI/GPT Bootable disk image" (read: cloud-images.ubuntu.com, 2 Oct 2026) | the live-server ISO, about 3 GB (assumed) |
| install | none: the image is already installed. First boot runs cloud-init, which creates the account and installs packages | Subiquity partitions and copies, then reboots: two boot phases, as Windows has (assumed: 5 to 15 minutes) |
| unattended | a second CD labelled `CIDATA` holding `user-data` and `meta-data`; ISO9660 or FAT both accepted (read: cloud-init's NoCloud page) | also a NoCloud seed, but Subiquity asks "Continue with autoinstall?" unless `autoinstall` is on the kernel command line, so the ISO must be remastered or GRUB typed at (assumed) |
| typing at a boot prompt | none expected (to measure) | likely, and typing at boot prompts is this project's worst trap (`vm.go:488-497`, `vm_create.go:1146-1160`) |
| what it resembles | a cloud VM or CI runner, which is what a claude-rig worker usually is | a machine installed by hand |

**Recommend the cloud image.** It removes the stage that costs Windows 45
minutes and all of its keystrokes, and the seed CD is built by code the tool
already has: `isoBuildImage` writes an ISO9660 image with Joliet through
go-diskfs (`internal/utmvm/iso.go:610-628`). Its volume label is the constant
`"UNATTEND"` (`iso.go:627`); the seed needs `cidata`, so the label becomes a
parameter.

### QEMU backend or Apple Virtualization backend

| | QEMU backend (what Windows uses) | Apple Virtualization backend |
|---|---|---|
| guest agent: `utmctl exec`, `file push`, `file pull`, `ip-address` | yes | **no.** `withGuestAgent` throws `operationNotSupported` unless the VM is a `UTMQemuVirtualMachine` (read: UTM `Scripting/UTMScriptingVirtualMachineImpl.swift:215-225` at v4.7.5). UTM's scripting reference says of the whole guest suite "Only supported on QEMU backend" (read) |
| keystrokes and mouse from the host | yes | no: "Only supported on QEMU backend" (read, same page) |
| `config.plist` | the template the tool already writes and has verified against 4.7.5 | a different schema (`UTMAppleConfiguration`): a second template, and a second source of "cannot import this VM" |
| speed | hardware-accelerated (`Hypervisor` true, `config.plist.tmpl:32`) | faster disk and boot (assumed) |
| extras | | Rosetta for x86-64 Linux binaries, virtiofs shares |

**Recommend QEMU.** Without the guest agent, readiness (`AgentReady` asks
`utmctl ip-address`, `vm.go:238-257`), running anything in the guest
(`appExecSteps`, `app.go:279`) and `vm-ssh-create` would each need a second
route for Linux only. That is the duplication
[Conventions](../docs/CONVENTIONS.md#one-way-to-do-each-thing) forbids. What is
given up is Rosetta, which matters only for x86-64 binaries.

### The VM's shape

What UTM's own wizard chooses for a Linux guest on QEMU `virt` (read:
`Platform/Shared/VMWizardState.swift` and `UTMQemuConfigurationDrive.swift` at
v4.7.5), against what the tool writes for Windows:

| | Windows today | Linux, proposed | why |
|---|---|---|---|
| system disk | NVMe (`vm_create.go:473`) | **VirtIO** | the wizard's default for `virt` (`UTMQemuConfigurationDrive.swift:125-131`); Linux has the driver inbox. NVMe is in the tool only because Windows Setup lacks one |
| display | `virtio-ramfb-gl` (`vm_create.go:695-698`) | **`virtio-ramfb`** | the wizard picks `virtio-gpu-pci` (`VMWizardState.swift:464-469`), but that shows nothing until a guest driver loads ([traps](../docs/TRAPS.md#host-utm-and-the-iso)), so firmware and GRUB would be invisible to `vm-screen`. ramfb shows them. No `-gl`: nothing here needs 3D |
| TPM | on (`config.plist.tmpl:34`) | off | the wizard sets it for Windows only (`VMWizardState.swift:458`) |
| clock | local time (`config.plist.tmpl:38`) | UTC | Linux expects UTC |
| network | `virtio-net-pci`, Shared | the same | inbox driver on Linux |
| icon, notes | `windows`, "login dev/dev" (`config.plist.tmpl:12-14`) | `linux`, its own note | |
| memory | 8 GiB, clones 4 GiB (`capacity_model.go:21,29`) | **2 GiB** for every Linux VM | [budget](#disk-and-memory-on-a-16-gib-mac); to measure with the rig running |
| CPUs, disk size | 4, 64 GiB sparse | the same | one shape; a sparse disk costs nothing until written |

It stays **one template** with more values filled in, not a second file.
Because a rejected plist names no field, the change is proven by running both a
Linux create and a Windows create (Conventions, "Do not").

**The disk.** The tool's system disk is a raw sparse file, `Data/disk.img`
(`vm.go:80`, `createSparse` at `vm_create.go:526`), and the capacity model
measures that path (`capacity_model.go:119-127`). Ubuntu publishes the image as
qcow2 only. Two ways to keep one kind of disk:

- **Convert to raw on the Mac, in Go** (recommended):
  [lima-vm/go-qcow2reader](https://github.com/lima-vm/go-qcow2reader)'s
  `convert` writes a raw file and skips zero extents, so it stays sparse (read:
  its README; Apache-2.0, no dependencies in its `go.mod`). Then `Truncate` to
  64 GiB and let cloud-init grow the root partition. One new dependency, so the
  [licence table](../docs/CONTRIBUTING.md#licence) is re-checked. To measure:
  that it reads Ubuntu's compressed image.
- **Keep qcow2.** UTM passes no `format=` for a drive (read:
  `UTMQemuConfiguration+Arguments.swift:842-884`), so QEMU would probe it. But
  growing it needs `qemu-img`, which UTM runs only inside its own helper
  (`Services/UTMQemuImage.swift`), not as a command this tool can call.

**Download and verify.** `isoDownload` already resumes a `.part`, takes a
SHA-256 and renames only on a match (`iso_create.go:351-373`). Pin one dated
release of the image with its SHA-256 as constants, as the Windows catalog
entry is pinned: "a VM that differs between two machines gives results that
cannot be compared" (`docs/USING.md:145-148`). The `current/` directory changes
daily and is not used.

### What must be measured first

None of these can be reasoned out. Each gets a dated line in
[RESULTS.md](../docs/RESULTS.md), and the first three decide whether the
recommendation stands.

| # | question | why it matters | if the answer is bad |
|---|---|---|---|
| M1 | Does UTM's firmware boot the cloud image's disk on a fresh VM with nothing typed? | `vm.go:479-486` says the firmware "does not auto-select a boot entry" and drops to the UEFI shell; clones of Windows boot untyped because their `efi_vars.fd` holds an entry. A new Linux VM has none and relies on the fallback path `\EFI\BOOT\BOOTAA64.EFI` | put `startup.nsh` on the seed CD; if that fails too, `bootAssist` types one path once, into a shell this code just started |
| M2 | Does cloud-init read a seed CD made by go-diskfs (label `cidata`, Joliet, no Rock Ridge)? | the docs' example uses `-joliet -rock`; Joliet-only is untested. The Windows answer file had exactly this class of failure (traps: FAT disk, Joliet off, padding) | add Rock Ridge, or write the seed as FAT, which cloud-init also accepts |
| M3 | Do `utmctl ip-address`, `exec`, `file push` and `file pull` work against Linux's `qemu-guest-agent`? | everything else stands on them. UTM always attaches the agent's port (read: `UTMQemuConfiguration+Arguments.swift:1102-1118`); the guest side is assumed | no fallback inside this design: reconsider |
| M4 | Time from start to an answering agent: first boot (cloud-init, `apt` installing the agent) and later boots | sets the timeouts and what `vm-create` says | |
| M5 | Does UTM's `duplicate` clone a VirtIO raw disk as it clones NVMe (instant, sparse, new UUID), and do two clones get different addresses? | Ubuntu's DHCP client identifies itself by machine-id, not MAC (assumed), so two clones with one machine-id may get one lease even with different MACs: the Linux form of the MAC trap | seal with an empty `/etc/machine-id`, or set `dhcp-identifier: mac` in the seed's network config |
| M6 | Does the network come up on a clone with a new MAC? | cloud-init may write a netplan file that matches the first boot's MAC (assumed) | supply `network-config` in the seed matching by interface name |
| M7 | Does a guest `fstrim` punch holes in the raw file on the host? | measured yes for Windows TRIM (RESULTS, "A VM of your own in 23 s"); UTM passes `discard=unmap` for every writable drive (read, line 878) | the golden image is larger; nothing breaks |
| M8 | Memory: does the rig (Claude Code, mise, node) run in 2 GiB? | the budget below depends on it | 4 GiB, and one fewer VM fits |
| M9 | What a Linux clone writes of its own over a session (APFS private bytes) | `cloneReserveBytes` is 4 GiB from a Windows measurement (`capacity_model.go:44-55`) | a per-OS reserve |
| M10 | Does a `sudo reboot` inside the guest come back with the agent answering, untyped? | claude-rig's reboot test needs it | `vm-create` on the stopped VM boots it, as today |

## 2. What the guest needs for the tool's contract

| need | Windows today | Linux, proposed |
|---|---|---|
| **account** | `dev`, an administrator, password `dev` in the answer file, auto-logon (`docs/USING.md:157-160`) | `dev`, in `sudo` with `NOPASSWD`, **password locked**: no password works anywhere. claude-rig's bootstrap needs root through `sudo` and has not been tested where sudo asks (its backlog). Created by cloud-init |
| **guest agent** | from UTM's guest tools CD, runs as SYSTEM | `qemu-guest-agent`, the package UTM's Linux page names (read). Not in the cloud image (assumed, from several write-ups), so cloud-init installs and starts it on the first boot, which needs the network. Runs as root |
| **readiness** | `utmctl ip-address` answers (`vm.go:238-257`) | the same call, unchanged |
| **running something and getting its output** | a batch file pushed and run by path, output and exit code captured to files and pulled, because `utmctl exec` returns neither (`app.go:85-120`, `app.go:279-332`) | the same flow with a shell script: UTM's `exec` defect is on the host side (UPSTREAM, "`utmctl exec` never returns the guest's output"), so it applies to any guest |
| **SSH** | `vm-ssh-create` installs the OpenSSH Server capability, 9 min 46 s the first time (`docs/RESULTS.md:37-55`) | `openssh-server` is in the image, stopped and disabled. `vm-ssh-create` enables it, seconds |
| **a binary in, output back** | SMB share served by the guest, pure-Go client on the Mac (`app_share.go`) | [below](#how-a-binary-gets-in) |
| **desktop session** | auto-logon, `-gui` through a scheduled task | **none.** Server image, no desktop |

### How vm-ssh-create generalises

Most of `vm_ssh.go` is not about Windows: reading and checking the public key
(`:60-121`), pushing a script and the key as a file (`:131-139`), running the
script, then asking the guest for its own addresses in the same batch
(`:186-203`), and reading an SSH banner from the Mac (`:240-262`). What is
Windows is data:

| | Windows | Linux |
|---|---|---|
| the script | `assets/vm-ssh.ps1`, run by `powershell` (`vm_ssh.go:24,187`) | `assets/vm-ssh.sh`, run by `sh` |
| the address command and its parser | `ipconfig`, `ipconfigIPv4` (`vm_ssh.go:41`, `app_share.go:211`) | `ip -4 -o addr`, its own parser |
| where the key goes | `C:\ProgramData\ssh\administrators_authorized_keys` | `~dev/.ssh/authorized_keys`, mode 600 |
| who may log in | `-user` "must be an administrator" (`cmd/irgo-winvm/vm.go:279`) | `-user`, default `dev` |
| the firewall | the tool's own rule, local subnet | none on the image (assumed); the script sets `PasswordAuthentication no`, which Windows cannot claim ([threat model](../docs/THREAT-MODEL.md#ssh-into-a-guest)) |
| the undo | stop and disable `sshd`, remove every key, check port 22 is closed | the same |

The printed last line, the exit codes, the lock and the "cheap to repeat"
behaviour do not change. Host keys: the script generates any that are missing
(`ssh-keygen -A`), so an image sealed without them gives each clone its own.

### How a binary gets in

`Push` (`app.go:132-154`) has three routes: under 256 KiB straight through
`utmctl file push`; otherwise SMB; otherwise zipped through `utmctl` at about
0.4 MB/s. The first and third are the guest agent's and should work on Linux
with a different unpack command (to measure, M3). The fast route is the choice:

| option | reuses | adds | cost |
|---|---|---|---|
| **A. Samba in the guest** (recommended) | all of `pushShared`: dial, NTLM login, signed write, then move and hash in the guest (`app_share.go:63-110`). Only the move and hash commands differ | the `samba` package in the image, an SMB-only password for `dev`, port 445 | a daemon and tens of MB in the image (to measure) |
| B. SFTP over the guest's sshd | nothing of the SMB path | `golang.org/x/crypto/ssh` and an SFTP client; a key pair the tool owns | `sshd` must always be on, so `vm-ssh-delete` can no longer check that port 22 is closed, and every clone carries the tool's key |
| C. the guest agent only | routes one and three, no new code | nothing | an 8 MB binary takes 12 to 14 s (Windows figure, ARCHITECTURE "How a binary gets into the guest") |

A reuses the most and keeps `vm-ssh-create` and its undo meaning the same on
both systems. C is there in any case as the fallback, so phase 3 ships on C,
measures it, and adds A only if the number is bad. Phase 1 needs none of this:
claude-rig drives its VM over SSH.

### Desktop

`-gui` exists because the Windows agent runs in session 0 with no desktop
(`docs/USING.md`, "Why `-gui` exists"). A server image has no desktop at all,
so `app-create -gui` on a Linux VM is refused with exit 2 and a sentence.
**`vm-screen` works from the first phase**: it photographs UTM's window from
the host (`vm_screen.go:36-56`) and needs nothing in the guest. A Linux
desktop for glaze is a separate piece of work with its own questions (which
desktop, WebKitGTK, how a program reaches the session) and is not planned here.

## 3. How it fits the command scheme

### One guest description, not two implementations

Windows assumptions in the code, counted 2 Oct 2026 in non-test Go under
`internal/`, `cmd/` and `wire/`:

| assumption | lines | files | where most of it is |
|---|---|---|---|
| `cmd.exe`, `.bat`, `powershell`, `.ps1` | 40 | 9 | `app.go`, `app_create.go`, `vm_repair.go`, `vm_ssh.go` |
| `C:\` paths | 39 | 9 | `app.go`, `app_delete.go`, `app_create.go` |
| `.exe` | 59 | 23 | `app.go`, the command summaries, `remote/client.go` |
| `schtasks`, `certutil`, `ipconfig` | 28 | 3 | `app_share.go`, `vm_ssh.go`, `app_create.go` |
| SMB | 23 | 5 | `app_share.go` |
| the name `win11` | 24 | 13 | `iso.go`, `vm.go`, `vm_create.go` |

They sit in the app stage and the guest scripts. The vm stage's host side
(`vm_utm.go`, `vm_start.go`, `vm_delete.go`, `vm_lease.go`, `vm_capacity.go`,
`lock.go`, `vm_screen.go`) names Windows only in comments and messages.

So: one small type inside `internal/utmvm` (the package is not split) that
answers, for a guest OS, the questions the shared code asks: the scratch
directory, the script extension and interpreter, how an argument is quoted, how
a script captures output and exit code, the move, hash, unpack and address
commands, the default account, which asset is the SSH script, which is the seal
script. `appExecSteps`, `Push`, `VMSSHCreate`, `AppDelete` and the seal take it
and keep their single body. Windows' values are the present constants, moved,
with no behaviour change: that is its own commit, verified on a Windows clone
before any Linux value exists.

**How a command knows the VM's OS.** From the VM's record,
`vms/<name>.json` (`vm_lease.go`), which gains an `os` field written by
`vm-create`. A VM without a record, or with a record without the field, is
Windows: that is every VM that exists today (`irgo-win11`, the golden image,
clones made before this). A record that cannot be read is cannot tell, and
refuses.

### What each command becomes

| command | change |
|---|---|
| `vm-create` | gains **`-os windows\|linux`**, default `windows`. `-os linux -install -golden=false` builds a VM from the cloud image; `-os linux` clones the Linux golden image when there is one. On an existing VM, an `-os` that disagrees with its record is exit 2 |
| `vm-delete`, `vm-screen`, `status`, `capacity`, `vm-reap`, `prune`, `doctor` | no flag. `status` and `capacity` show the OS. `doctor` gains the Linux image rows |
| `vm-ssh-create`, `vm-ssh-delete` | no flag; OS from the record ([above](#how-vm-ssh-create-generalises)) |
| `vm-golden-create -vm <src>` | no flag: the source VM's OS decides the seal script and the image's name |
| `vm-golden-delete`, `vm-golden-push`, `vm-golden-pull` | gain `-os`, default `windows`, to say which image |
| `app-create`, `app-delete`, `app-upload` | no flag (phase 3). `app-create` checks the file is for the VM's OS before pushing: `MZ` for Windows, as `remote/client.go:218-221` already checks, ELF for AArch64 on Linux; a mismatch is exit 2 |
| `iso-create`, `iso-delete` | **Windows only**, unchanged. Linux has no installer |
| `vm-repair`, `app-create -gui`, `glaze-check -windows` | **Windows only**; on a Linux VM, exit 2 saying so |
| `vm-check`, `vm-status` | Windows only until phase 5 |
| `remote-submit`, `serve` | Windows only until phase 6 |

**`irgo-win11` stays the only default VM** (`vm.go:28`). There is no owner's
Linux VM, so a Linux VM always has a `-vm` name. Leaving `-vm` out with
`-os linux` is exit 2.

**No new media command.** The cloud image is fetched by the `vm-create` that
needs it, into `media/`, as the guest tools are fetched today
(`vm_utm.go:94-130`); `prune` bounds it and `doctor` and `capacity` list it.
A `linux-image-create` beside `iso-create` would be a second way to answer
"where does media come from".

### What "golden image" means for Linux

The same thing: a stopped VM registered with UTM that every new VM is cloned
from, here **`irgo-golden-linux`** beside `irgo-golden`
(`vm_golden.go:30`), each with its own manifest. It is made the way the
Windows one is:

    vm-create -os linux -vm g1 -install -golden=false    # cloud image, first boot
    vm-golden-create -vm g1                              # seal, clone as the image, verify

The seal in the guest is a shell script in place of `vm-golden-seal.ps1`:
`cloud-init clean`, empty `/etc/machine-id`, remove the SSH host keys and every
authorized key, clean the package cache, `fstrim`, shut down from inside. Then
the existing steps: clone through UTM keeping only the system disk, clone that
once more, boot it until its agent answers, delete it
(ARCHITECTURE, "The golden image: sealing and cloning"). Two edits to shared
pieces: `utm-clone.applescript:37-39` keeps "the one NVMe disk" and must keep
"the one system disk" for the VM's interface, and `protectedVM`
(`vm_lease.go:167-168`) gains the Linux names.

It differs from Windows in what it is *worth*. A Windows golden image saves 45
minutes; a Linux one saves the first boot's minute or two and its network
dependency. That is why phase 1 ships without it.

### What app-create means for a Linux binary

`GOOS=linux GOARCH=arm64 CGO_ENABLED=0 go build`, then
`app-create -vm <linux vm> ./hello [args]`: pushed to a scratch directory,
made executable, run, output and exit status back, with the same exit codes
(1 is the program, never the tool). It runs as root, as a Windows program runs
as SYSTEM, since the agent starts it; `-user` runs it as that account. No
`-gui`.

### The product name

"irgo-windows-vm" and "irgo-winvm" describe one of two guests once this lands.
The name is in 529 places as `irgo-winvm` and 242 as `irgo-windows-vm`
(counted 2 Oct 2026, whole tree), and in things outside the tree. The options,
not chosen here:

| option | cost |
|---|---|
| **keep both names**; the docs say "Windows and Linux VMs" | nothing. The name misleads a newcomer |
| **rename the binary only** (for example `irgo-vm`) | the cask, `install.sh`, the release asset names, every `.mcp.json` that registers it (claude-rig's included), the seven `IRGO_WINVM_*` variables, and the runtime folder `~/Library/Application Support/irgo-winvm/`, which needs a migration or stays under the old name |
| **rename the repository too** | all of the above, plus the Go module path, the Pages URL that every error message links (`utmvm.SiteURL`), and the Worker's hostname. GitHub redirects the repository; it does not redirect Pages or the module path |
| **decide it with claude-rig** | its backlog already asks "whether the repos merge" and for "shared naming". A rename now and a merge later is two renames |

## 4. The seam to claude-rig

What claude-rig's tests need from a Linux VM, and nothing more:

| need | command | from phase |
|---|---|---|
| a fresh Ubuntu machine with systemd, `sudo` without a password, internet | `vm-create -os linux -vm rig-linux` (phase 1: with `-install -golden=false`, minutes; phase 2: a clone, seconds) | 1 |
| SSH in with the Mac's key | `vm-ssh-create -vm rig-linux -key ~/.ssh/id_ed25519.pub` | 1 |
| its address | the last line of that command, `ssh dev@<address>`; run again for the current one | 1 |
| throw it away | `vm-ssh-delete`, `vm-delete -vm rig-linux -force` | 1 |
| see what exists | `status` | 1 |

With these, `mise run push dev@<address>` in claude-rig rigs the VM exactly as
it rigs the OrbStack VM today, and its backlog's "One-line bootstrap on a real
Linux machine with systemd" and "fleet" rows can name a UTM VM instead.

Things claude-rig should know, to carry into its own backlog (this plan does
not edit that repository):

- **Hostnames.** Every Windows clone is `WIN11ARM` (ARCHITECTURE, "No
  sysprep"). A rigged machine shows in the Claude app under its own name, so
  two clones with one name cannot be told apart. Phase 2 sets a Linux clone's
  hostname to its VM name.
- **Two test VMs and memory.** [The budget](#disk-and-memory-on-a-16-gib-mac):
  a Windows clone and a Linux VM run together only while `irgo-win11` is
  stopped, or with `-overcommit`.
- **Its "run the rig before sealing" item** works for Linux after phase 2 with
  no further change here: create, `vm-ssh-create`, push the rig,
  `vm-ssh-delete`, `vm-golden-create`. The rig's login must not be sealed in;
  that is claude-rig's to guarantee.
- **Its "run a shell command in the guest" item** is met for Linux by SSH, and
  not otherwise addressed here.

### The related item: OpenSSH Server in the Windows golden image

The first `vm-ssh-create` on a fresh Windows clone took 9 min 46 s, nearly all
of it Windows installing the capability, and 16 s on a repeat
(`docs/RESULTS.md:37-55`). Phase 4 installs the capability while sealing and
leaves `sshd` **never started**: no host keys exist yet, no authorized keys,
no firewall rule. That keeps the threat model's warning intact ("Seal a VM
that never had `vm-ssh-create` run on it": clones of an image sealed with SSH
on would share host keys). It is independent of every Linux phase and can land
at any time.

## 7. Risks and unknowns

**The boot (M1) is the largest unknown.** Everything painful in this
repository's history is a boot prompt nobody saw. If the firmware does not
boot the disk by itself, the fallbacks exist, but phase 1 grows.

**Traps a Linux guest would also hit** (from [TRAPS.md](../docs/TRAPS.md)):

| trap | Linux form |
|---|---|
| `utmctl exec` returns no output and exits 0 | the same: host-side. The capture-to-file flow is kept |
| `utmctl ip-address` hangs with no agent | the same: every call keeps its deadline. Until cloud-init has installed the agent, a new VM looks exactly like a hung one, so `vm-create` says what it is waiting for and photographs it |
| `utmctl file push` at 0.4 MB/s | the same, expected |
| clones keep the source's MAC | the same; `cloneVM` already sets and checks it. Plus the machine-id form (M5) and the netplan MAC match (M6) |
| a seed medium the installer silently ignores (FAT, Joliet off, padding, a long comment) | cloud-init ignoring the seed looks like a VM that boots to a login prompt with no `dev` account and no agent. `vm-create` must time out saying that, with a screenshot (M2) |
| a rejected `config.plist` names no field | the same; the template change is proven by running both systems |
| UTM's container cannot be read or written | the same; staging and import are reused |
| the guest cannot connect to the Mac | the same; pushes stay Mac-to-guest |
| `virtio-gpu-pci` shows nothing | avoided by `virtio-ramfb` |
| keystrokes typed at a running VM | not needed if M1 passes; if it fails, the rules in `vm_create.go:1146-1160` apply unchanged |
| a guest that updates itself and takes the agent away | Ubuntu's unattended upgrades can restart services or hold `apt`'s lock while the rig installs packages (assumed). To decide in phase 1: leave them on, as a real machine has, and say so |

**New to Linux:** the first boot needs the network (to install the agent); an
offline Mac cannot make the first VM. Phase 2's image removes that for every
VM after the first.

**Licensing.** The Windows golden image may not be passed to anyone, which is
why its cache is private and local (ARCHITECTURE, "Local only"). A Linux image
has no such limit: Ubuntu's cloud images are free to download and the software
in them is redistributable (assumed in general; to check before phase 7:
Canonical's trademark policy for a *modified* image offered under the Ubuntu
name, and the GPL's source-offer duty for whoever hosts binaries). What that
enables: a public image, pulled with no token by any Mac or CI job; no
per-clone licence, so the number of Linux clones is bounded only by the
machine; and screenshots and disk images that can be attached to issues.

### Disk and memory on a 16 GiB Mac

Memory, by the guard's own rule (configured memory of every VM not stopped,
plus the new one, must leave 4 GiB; `capacity_model.go:36`):

| running | Linux VM of 2 GiB | left | verdict |
|---|---|---|---|
| nothing | 1 | 14 | yes |
| `irgo-win11` (8) | 1, or 2 | 6, or 4 | yes |
| one Windows clone (4) | 1 | 10 | yes |
| `irgo-win11` and one Windows clone (12) | 1 | 2 | **refused** (exit 7) without `-overcommit` |

So claude-rig's "Windows VM and Linux VM side by side" fits beside a stopped
`irgo-win11`, not a running one. At 4 GiB per Linux VM (if M8 fails) the second
row becomes one VM, not two.

Disk: on 1 Oct 2026 the Mac had 38.2 GiB free (`docs/USING.md`, "Is there
room?"). Linux adds the cached download (0.6 GB), a golden image of an
estimated 2 to 3 GiB, and each VM's 4 GiB reserve. The guard needs the
reserve plus what is promised plus 10 GiB, so two Linux VMs and the image fit
with room; the per-owner quota of 2 VMs (`capacity_model.go:75-78`) is met
exactly by one Windows and one Linux VM.
