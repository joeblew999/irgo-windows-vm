# UTM 5: stay on 4.7.5, trial 5.x on a disposable VM, adopt when stable

Status: **assessed from source; code for the version check landed; trial not
run** · 2026-09-30

The owner noticed UTM v5.0.6. The Mac has **UTM 4.7.5**, which is the latest
**stable** release (3 Jan 2026). 5.0.0–5.0.6 are **pre-releases** (5.0.6 on 24
Sep 2026), and no date has been given for 5.0 stable: the `v5.0` milestone is
open with no due date (5 open, 76 closed). Nothing was installed, upgraded,
quit or restarted, and the running VM was not touched. Every verdict below
comes from reading the source at both tags (`utmapp/UTM` v4.7.5 and v5.0.6,
diffed; QEMUKit at the revision 5.0.6 pins), plus the release notes and issues.
None of it has been run.

## Recommendation

1. **Stay on 4.7.5** on this Mac and on `irgo-win11`. It is the stable
   release, the config is verified against it (`utmvm.VerifiedVersion`), and
   5.x fixes none of our five `utmctl` findings, so upgrading gains nothing we
   use.
2. **Trial 5.x on a disposable VM** when the VM machine is free, following
   [the procedure below](#trial-procedure-for-when-the-vm-is-free). The source
   says it should work: the config format, the `utmctl` commands we call, clone
   and AppleScript are unchanged. The risks are in what QEMU is given and in
   the guest tools, and only a real install can settle those.
3. **Adopt when 5.0 goes stable**, and only after the trial passes. Then:
   - bump `VerifiedVersion`;
   - decide the guest-tools URL (see risk 3);
   - re-run the trial against the stable build.

   Until then, `irgo-winvm doctor` says a newer stable release exists as soon
   as one is published.

**The decision to make before 5.0 goes stable.** `vm-create` installs the
latest **stable** release on a machine with no UTM. On the day 5.0 is marked
stable, a fresh machine gets 5.0, with only the "different major version"
warning from `DetectUTM`. If the trial has not passed by then, cap the
installer at the verified major (a filter in `pickUTMReleases`) until it has.

## What changed in the code (this plan's commits)

- **`vm-create` installs the latest stable release, and the choice is
  explicit and tested.**
  - Before: it used GitHub's `/releases/latest`, which already skips
    pre-releases, so it installed 4.7.5, but by GitHub's rule, not ours.
  - Now: `latestStableUTMDMG` (`internal/utmvm/utm_release.go`) lists the
    releases and `pickUTMReleases` chooses by version number. It skips drafts,
    pre-releases and releases without `UTM.dmg`.
  - When GitHub lists no stable release, the result is an error, never a beta.
  - Twelve negative controls were run by hand; each is recorded in its test's
    comment.
- **`irgo-winvm doctor` (and `doctor -json`)** adds four rows:
  - `UTM version`: the installed version;
  - `UTM latest stable`;
  - `UTM latest beta`;
  - `UTM update`: `available`, `none` or `cannot tell`, with a sentence.
  - The answer comes from `~/Library/Application Support/irgo-winvm/utm-releases.json`
    if it is under 12 hours old, else from GitHub within 3 s, else from an
    older cache marked stale. Offline it says "cannot tell" and gives the
    reason; that is not an error.
  - No test touches the network: `cmd/irgo-winvm` stubs it in `TestMain`, and
    `internal/utmvm` uses an `httptest` server.

Sample, on this Mac, 30 Sep 2026:

```
UTM.app                1.9 GB       /Applications/UTM.app
UTM version            4.7.5        /Applications/UTM.app
UTM latest stable      4.7.5        https://github.com/utmapp/UTM/releases/tag/v4.7.5
UTM latest beta        5.0.6        https://github.com/utmapp/UTM/releases/tag/v5.0.6
UTM update             none
...
UTM 4.7.5 is the latest stable release; no update. 5.0.6 (24 Sep 2026) is a pre-release; vm-create never installs one.
```

Offline (no cache, network refused), in under a second:

```
UTM latest stable      cannot tell
UTM latest beta        cannot tell
UTM update             cannot tell
Cannot tell whether UTM 4.7.5 is up to date: asking GitHub for UTM's releases: Get "https://api.github.com/...": proxyconnect tcp: dial tcp 127.0.0.1:1: connect: connection refused.
```

## Our five `utmctl` findings under 5.0.6

The repros are in [`2026-09-30_1800_upstream-reports.md`](2026-09-30_1800_upstream-reports.md)
§5–§9. The detail is in [docs/UPSTREAM.md](../docs/UPSTREAM.md#utm).

| finding | evidence at v5.0.6 | verdict |
|---|---|---|
| **A. exits 0 on failure** | `EventErrorHandler.eventDidFail` still writes to stderr and returns `nil`. 5.x adds `hasFailed = true` (line 151), read only by `SnapshotCreate` (line 853: `guard !EventErrorHandler.shared.hasFailed else { throw ExitCode.failure }`). 4.7.5 has no `hasFailed`. Related: #5377 (open), #7858 (`utmctl --help` exits 134, open) | **not fixed** (half-plumbed) |
| **B. `exec` returns no output** | identical code: `executeAt!(…, outputCapturing: true)`, then `repeat { … } while result["hasExited"] as? Bool == false`, then `exitCode … ?? 0`. If the record lacks `hasExited`, the loop runs once and exits 0 with no output (unverified). No `--output` or `--wait` added | **not fixed** |
| **C. `suspend --save-state` power-cut** | `determineSnapshotSupport()` is unchanged (4.7.5:262/267, 5.0.6:289/294). It refuses a `-gl` display, then NVMe, so our VM can never save state; the thrown error then meets finding A. 5.x adds offline disk snapshots for a **stopped** VM (`UTMQemuFrozenSnapshotBackend`), which do not go through this check. #3819 (open since 2022); #7916 (5.0.6 loses older suspend states, open) | **not fixed**; the refusal is by design |
| **D. `ip-address` hangs** | the QEMU path is unchanged; 5.0.3 added an ARP lookup for the Apple backend only (#7643). QEMUKit has 1 s / 10 s RPC timeouts (`QEMUManager.m:89`), so the hang is elsewhere: possibly the synchronous write before the timed wait, or no Apple Event timeout in utmctl (both unverified). #7799 (RPC timeout, Win11, 5.0.3, open) | **not fixed** |
| **E. rejected config names no field** | `Platform/UTMData.swift`: `guard let _ = try? VMData(url: url) else { throw UTMDataError.importFailed }` at 4.7.5:677/711/734 and 5.0.6:690/724/747 | **not fixed** |

The drafted reports stay valid against 5.x. When filing, say "reproduced on
4.7.5; the code is unchanged at v5.0.6", and for §9 quote the `try?` line
above.

## Compatibility risks, in order

1. **QEMU arguments change under our VM.** GICv3 is now always on, and
   `virtio-ramfb-gl` gets Venus/Vulkan/DirectX blob arguments by default. A
   fresh install on 5.x meets both from its first boot. An **existing**
   `irgo-win11` would switch from GICv2 to GICv3 at its next boot under 5.x,
   and back again under 4.7.5. Windows' tolerance of that is unverified, so
   `irgo-win11` is never started under 5.x. To turn the 3D arguments off (from
   source, untested): Settings → set the Vulkan and DirectX drivers to
   Disabled (`QEMUVulkanDriver` and `QEMUDirectXDriver` = 1 in UTM's
   defaults). These are app-wide.
2. **Open Windows 11 beta bugs.**
   - #7850: install hangs after "starting BootXXXX", 5.0.5, M4 Max, whatever
     the GPU, storage or TPM setting.
   - #7912: D3DMetal "Display not active". The 5.0.6 notes tell users who need
     it to stay on the previous version.
   - #7884 and #7825: the uninstall script for the old display driver hangs or
     corrupts Windows.

   Our unattended install is exactly the path #7850 describes.
3. **Guest tools.** UTM 5 downloads `utm-guest-tools-3d-latest.iso` to a new
   file name. Ours still fetches `utm-guest-tools-latest.iso`, and `doctor`
   and `GuestToolsISO` look for that name.
   - On 5.x a VM we create gets the older 0.1.271 tools: no 3D driver, which
     is probably what we want.
   - UTM's own "Install Windows guest tools" would fetch the other file, so
     the comment "UTM and every VM generated afterwards pick it up" stops
     being true.
   - Moving to the 3D tools means the uninstall script first (#7884, #7825).
   - Decide at adoption; not before.
4. **Shared state between two UTMs.** A second copy of the app has the same
   bundle id (`com.utmapp.UTM`). It therefore shares the container
   `~/Library/Containers/com.utmapp.UTM`, the VM registry, the preferences
   and the guest-tools cache with 4.7.5.
   - "Side by side" is two binaries, not two environments. A beta launched
     next to 4.7.5 sees `irgo-win11` and can start it.
   - The tool hard-codes `/Applications/UTM.app` (`utmvm.AppPath`) and its
     `utmctl`, so a beta at any other path is not what the tool drives.
5. **Suspend state is not portable.** A state saved by 5.x (a UUID name)
   cannot be resumed by 4.7.5, which looks for `"suspend"`, and #7916 loses
   older states on 5.0.6. We only use plain `suspend` (to memory), so this
   costs nothing as long as nothing is left suspended across a version switch.
   Stop, don't suspend, before switching.
6. **Schema drift is not a risk this time.** `config.plist` is version 4 with
   identical keys at both tags. The "cannot import" class of failure should
   not appear. If it does, it is new and belongs in UPSTREAM.md.

## Trial procedure for when the VM is free

Run it only when no other agent is using UTM: installing UTM restarts it and
stops every VM. **Never on `irgo-win11`.** Use the disposable names
`irgo-utm5` (full install) and `irgo-test-cycle` (the one `vm:test` uses).
Preferably do it on a second Mac. On this Mac it means swapping the app for
the length of the trial (risk 4), then swapping it back.

**0. Preconditions.**

```sh
irgo-winvm status                     # no job running
utmctl list                           # note every VM and its state; none "started"
irgo-winvm doctor -json > ~/utm5-before.json
```

If `irgo-win11` is started, stop it with `utmctl stop irgo-win11`, not
`suspend` (risk 5), and only if its owner agrees.

**1. Swap in 5.0.6, keeping 4.7.5 for rollback.** `InstallUTMFromRelease`
installs only stable releases, by design, so this step is manual.

```sh
osascript -e 'quit app "UTM"'
mv /Applications/UTM.app /Applications/UTM-4.7.5.app
gh release download v5.0.6 -R utmapp/UTM -p UTM.dmg -D /tmp/utm5
hdiutil attach /tmp/utm5/UTM.dmg -nobrowse -readonly -mountpoint /tmp/utm5/mnt
ditto /tmp/utm5/mnt/UTM.app /Applications/UTM.app
hdiutil detach /tmp/utm5/mnt
irgo-winvm doctor        # expect: UTM version 5.0.6, "newer than the latest
                         # stable release, 4.7.5: a pre-release", and "verified
                         # against UTM 4.7.5, a different major version"
```

Do not start `irgo-win11` while 5.x is installed.

**2. Create and delete.** This is the config and `utmctl` surface: does 5.x
import our `config.plist`, and do `status` and `delete` behave?

```sh
mise run vm:test
```

**3. Full unattended install on a disposable VM.** This is where risks 1–3
bite. About 45 minutes; watch `vm-screen` for the #7850 boot hang.

```sh
irgo-winvm vm-create -install -vm irgo-utm5
irgo-winvm vm-screen -vm irgo-utm5    # at intervals; compare with docs/screens/vm/
```

If it hangs at boot, retry once with the Vulkan and DirectX drivers set to
Disabled in UTM's settings (risk 1), and record which setting made the
difference.

**4. The glaze gate on it.**

```sh
irgo-winvm glaze-check -windows -vm irgo-utm5
```

The verdict should match the last `irgo-win11` run: `KNOWN BUGS ONLY`, with
only §1b failing. This rewrites the Windows section of `docs/GLAZE-STATUS.md`
and `docs/screens/conformance/windows/`. Keep that on a branch as the trial's
record; do not merge it as the Windows record.

**5. Re-check each `utmctl` finding.** Use the repros in
[`2026-09-30_1800_upstream-reports.md`](2026-09-30_1800_upstream-reports.md);
`U=/Applications/UTM.app/Contents/MacOS/utmctl`. §5 and §8 need a running VM
with no OS: `irgo-winvm vm-create -vm irgo-test-cycle` (no `-install`), then
`$U start irgo-test-cycle`.

| § | finding | repro | expected per source |
|---|---|---|---|
| 5 | exits 0 on failure | `$U ip-address irgo-test-cycle; echo $?` on a VM with no OS, and `$U delete <uuid>; echo $?` on an entry whose bundle is gone (recreate the phantom as UPSTREAM.md describes) | still 0 |
| 6 | `exec` output | `$U exec irgo-utm5 --cmd cmd.exe /c echo hello; echo $?`, then `… /c exit 3; echo $?` | nothing printed, 0 |
| 7 | `--save-state` | `$U suspend --save-state irgo-utm5; echo $?; $U status irgo-utm5`; then check the next boot for "Diagnosing your PC" with `vm-screen` | refused or power-cut; exit 0 |
| 8 | `ip-address` hang | `time perl -e 'alarm 120; exec @ARGV' $U ip-address irgo-test-cycle` (macOS has no `timeout`) | killed by the alarm at 120 s |
| 9 | config names no field | copy `irgo-utm5.utm`, delete `PS2Controller` from its `config.plist`, import it with `open -a UTM <copy>.utm` | the generic "cannot import" |

Record each result in docs/UPSTREAM.md under that finding's **UTM 5** line.

**6. Clone and import** (the golden-image plan):

```sh
utmctl stop irgo-utm5
time $U clone irgo-utm5 --name irgo-utm5-c1
/usr/libexec/PlistBuddy -c 'Print :Information:UUID' ~/Library/Containers/com.utmapp.UTM/Data/Documents/irgo-utm5-c1.utm/config.plist
/usr/libexec/PlistBuddy -c 'Print :Network:0:MacAddress' ~/Library/Containers/com.utmapp.UTM/Data/Documents/irgo-utm5-c1.utm/config.plist
```

Expect a new UUID and the same MAC, since `IsRegenerateMACOnClone` defaults
to off. Compare with the golden-image plan's 4.7.5 numbers.

**7. Clean up and roll back.** Delete the disposable VMs **while 5.x is still
installed**, so its registry forgets them, then put 4.7.5 back:

```sh
irgo-winvm vm-delete -vm irgo-utm5-c1 -force
irgo-winvm vm-delete -vm irgo-utm5 -force
irgo-winvm vm-delete -vm irgo-test-cycle -force
osascript -e 'quit app "UTM"'
rm -rf /Applications/UTM.app
mv /Applications/UTM-4.7.5.app /Applications/UTM.app
irgo-winvm doctor        # UTM version 4.7.5, update none
utmctl list              # irgo-win11 still there, as in ~/utm5-before.json
```

Start `irgo-win11` once under 4.7.5 and wait for the agent (`vm-repair`, no
`-reboot`). Also check whether 5.x left `snapshots.plist` in any bundle, and
whether 4.7.5 minds.

**8. Write down what happened.**
- Dated results go in docs/RESULTS.md.
- The finding verdicts go in docs/UPSTREAM.md.
- This plan moves to `done/` with a verdict: adopt at stable / not yet (why).
